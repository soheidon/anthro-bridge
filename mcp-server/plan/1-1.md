# 1-1. MCP サーバー実装プラン

## Context

`mcp-server` は、`anthro-bridge` リポジトリ内に独立して開発する Rust MCP サーバーである。

最初の目的は、Google Antigravity のような MCP 対応コーディングエージェントが、制御された小さなツールインターフェースを通じて外部 LLM を呼び出せるようにすること。最初のユースケースは次のとおり：

> DeepSeek V4 Pro を使って実装プランを生成し、呼び出し側エージェントにリポジトリ探索・編集・ビルド・テスト実行を任せる。

本サーバーは最初の段階では既存の Tauri GUI と意図的に分離する。動作検証後、MCP 実装を Anthro Bridge に統合し、既存のプロバイダ/モデル選択と API キー管理へ接続する。

## 調査で判明した既存実装（再利用の前提）

`gui/src-tauri/src/proxy.rs` と `gui/src-tauri/resources/config.json` から、DeepSeek 連携は以下の通り：

| 項目 | 値（既存 Anthro Bridge が使用中） | 出典 |
|---|---|---|
| エンドポイント | `https://api.deepseek.com/anthropic/v1/messages`（Anthropic 互換 Messages API） | config.json `upstream_url` + proxy.rs `.post("{}/v1/messages")` |
| 認証ヘッダ | `Authorization: Bearer <DEEPSEEK_API_KEY>` | proxy.rs `build_upstream_headers` |
| モデル ID | `deepseek-v4-pro` | config.json `default_model` / `model_map` |
| 推論設定 | `output_config.effort`（`low`/`high`/`max`。`medium`/`xhigh`→`high` に正規化） | proxy.rs `normalize_deepseek_reasoning_effort` / `apply_deepseek_reasoning_effort` |

SPEC 10 節の「Anthro Bridge が現在使うモデル ID を使う」指示から、**Anthropic 互換エンドポイント＋`deepseek-v4-pro`＋`output_config.effort`** をそのまま踏襲する。これが Phase 3（本体統合）で既存プロバイダアダプタを再利用する最短経路になる。

MCP SDK は現在、**`rmcp` が公式 Rust SDK**（`modelcontextprotocol/rust-sdk` に統合済み）。tokio ベース・async・stdio トランスポート対応。

## 主要な技術決定

| 決定 | 選択 | 理由 |
|---|---|---|
| MCP SDK | `rmcp`（公式 Rust SDK, stdio 用 `transport-io` フィーチャ） | 唯一の公式・アクティブ維持。tokio ネイティブ |
| 非同期ランタイム | `tokio` | 既存バックエンドと同一 |
| HTTP クライアント | `reqwest` | 既存 proxy.rs と同一 |
| エンドポイント | `https://api.deepseek.com/anthropic/v1/messages` | 既存実装を踏襲 |
| モデル | `deepseek-v4-pro` | config.json と同じ |
| 推論 | `output_config.effort: "high"` | プロバイダ層に固定（SPEC 10） |
| エラー型 | `thiserror` | 分類を型で表現（SPEC 11） |
| ログ | `tracing` + `tracing-subscriber` → **stderr** 固定 | stdout は MCP 専用（SPEC 12） |
| エディション | 2021 | 既存 Cargo.toml と一致 |
| HTTP モック | `wiremock`（dev-dependency のみ） | プロバイダテスト用 |

> **rmcp 実装上の注意**：実装時は現在の公式 Rust SDK の API を確認し、古いブログ記事の API をそのままコピーしないこと。tool 定義は可能な限り現在の `#[tool]` / `#[tool_router]` / `#[tool_handler]` + Serde/Schemars による schema 生成を使う。MCP protocol version や SDK 内部構造を独自実装しない。

## 型と責務の境界

「MCP プロトコル処理」と「プロバイダ HTTP」を分離するのが SPEC の本質。プロンプトの所有権は MCP 層、HTTP 詳細はプロバイダ層とする。プランナ契約は **system と user を分離**してプロバイダへ渡す（Anthropic Messages 互換形式へそのまま対応させるため）：

```rust
// provider/mod.rs
pub struct PlanResponse {
    pub text: String,
}

#[derive(thiserror::Error, Debug)]
pub enum ProviderError {
    #[error("provider not configured: {0}")]
    Config(String),          // API キー未設定など
    #[error("provider authentication failed: {0}")]
    Auth(String),            // 401 等（キー本文を含めない）
    #[error("provider request failed (HTTP {status}): {message}")]
    Http { status: u16, message: String },
    #[error("provider timeout: {0}")]
    Timeout(String),
    #[error("provider network error: {0}")]
    Network(String),
    #[error("provider returned an unusable response: {0}")]
    Response(String),        // 解析不能レスポンス
}

// Internal trait only.
// Native async fn in trait is sufficient here; async_trait is not required.
pub trait PlannerProvider: Send + Sync {
    async fn plan(
        &self,
        system_prompt: &str,
        user_prompt: &str,
    ) -> Result<PlanResponse, ProviderError>;
}
```

> クレート内部のみで使用し `dyn PlannerProvider` を作らずジェネリックに使うため、素の `async fn` で十分。public trait での `async fn` には lint が残るが、今回は対象外。

- `mcp.rs`：`plan` 引数を検証 → `build_system_prompt()`（定数）と `build_user_prompt(task, context, constraints)` で system / user を生成 → `provider.plan(&system, &user)` → 結果を MCP tool content に変換。
- `deepseek.rs`：system / user 文字列を受け取り、モデル・推論・認証・`max_tokens` を付与して HTTP 送信、`content[].text` を抽出して返す。**プロンプトの内容構造は知らない（system と user を分けて送るだけ）**。

## `plan` ツール定義

rmcp（公式 Rust SDK）の現行 API を使い、**手書きの `inputSchema` は登録しない**。Serde + Schemars による引数型から tool schema を生成させる：

```rust
#[derive(Debug, Deserialize, JsonSchema)]
struct PlanParams {
    task: String,
    context: String,
    constraints: Option<String>,
}
```

- `#[tool]` / `#[tool_router]`（tools-only server なら `#[tool_router(server_handler)]`）/ `#[tool_handler]` を使用。
- 下記 JSON は **外部から見た期待スキーマの説明** として残す（実装上は Schemars が生成する）：

```json
{
  "name": "plan",
  "description": "Generate an implementation plan for a software-development task using the supplied task, repository context, and constraints.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "task":        { "type": "string" },
      "context":     { "type": "string" },
      "constraints": { "type": "string" }
    },
    "required": ["task", "context"]
  }
}
```

検証：`task` 必須・非空、`context` 必須・非空、`constraints` 任意。エラーは MCP tool error として返す（SPEC 11 の「Input error」）。

## プロンプト契約（SPEC 7 を具現化）

- **システムプロンプト**（定数）：ソフトウェア実装プランナとして振る舞う、供給されたコンテキストのみに基づく、確実な事実と仮定を区別する、最小変更・スコープ外は触らない、対象ファイル/関数を正確に特定、順序付き手順・検証手順・不足情報の明示、変更済みと偽らない、偽のテスト結果を出さない、供給外のリポジトリアクセスを仮定しない。
- **ユーザープロンプト**（テンプレート）：`task` / `context` / `constraints`（あれば）をセクション分けして埋め込み。

`build_system_prompt()` と `build_user_prompt()` は純粋関数なので SPEC 16.2 のテスト対象になる。

## DeepSeek リクエスト/レスポンス

リクエスト（Anthropic Messages 形式）。**system と user を分離**して送る：

```json
{
  "model": "deepseek-v4-pro",
  "max_tokens": 8192,
  "system": "<planner system prompt>",
  "messages": [
    { "role": "user", "content": "<task / context / constraints>" }
  ],
  "thinking": { "type": "enabled" },
  "output_config": { "effort": "high" },
  "stream": false
}
```

`max_tokens: 8192` は初期値として妥当。planner 用途ではこれ以上増やさない。

レスポンスは `content` 配列から `type == "text"` の `text` を結合して返す。`reqwest` に timeout（例: 120s）を設定、2xx 以外は `Http` エラー、接続失敗/タイムアウトは `Timeout`/`Network`。**再試行ループは実装しない**（SPEC 10/23）。

## エラー分類（SPEC 11 → Rust）

| SPEC 分類 | `ProviderError` バリアント |
|---|---|
| Configuration（キー未設定） | `Config` |
| Input（task/context 欠落） | MCP 層で検証（プロバイダに渡さない） |
| Authentication（キー拒否） | `Auth` |
| Request（非 2xx） | `Http` |
| Timeout/Network | `Timeout` / `Network` |
| Response（解析不能） | `Response` |
| Internal MCP | `rmcp` のハンドラエラーとして返す |

いずれも API キー・認証ヘッダ・生の機微なリクエストダンプを含めない（SPEC 11）。

## テスト計画（SPEC 16 に対応）

`mcp-server/tests/` に配置。プロバイダの HTTP は `wiremock`（dev-dependency のみ）でモック：

1. **入力検証**：空 task → 拒否、task+context → 受理、constraints 省略 → 受理。
2. **プロンプト構築**：task/context/constraints が含まれる、プランナロール指示が含まれる、リポジトリアクセスを偽らない。
3. **プロバイダ要求**（mock サーバ）：モデル `deepseek-v4-pro`、`output_config.effort=high`、`Authorization: Bearer` 存在、API キーがエラーテキストに出現しない、成功時テキスト抽出、非 2xx→`Http`、タイムアウト→`Timeout`、不正レスポンス→`Response`。
4. **MCP ツール**：`plan` ツールのみ公開、ツール名/スキーマ一致、結果が tool content として返る、プロバイダエラーが clean な MCP エラーになる。
5. **stdout 規律**：ログが stdout を汚染しない（stderr 固定を確認）。
6. **実 API スモーク**（任意・最小限）：資格情報があれば 1 回だけ `plan → DeepSeek → テキスト` を確認。

## 実装順序（SPEC 25 を具体化）

1. `mcp-server/Cargo.toml` 作成（独立クレート。`rmcp` / `tokio` / `reqwest` / `serde` / `serde_json` / `thiserror` / `tracing` / `tracing-subscriber`。dev に `wiremock`）。
2. `src/provider/mod.rs`：`PlanResponse` / `ProviderError` / `PlannerProvider` trait 定義（`plan(system_prompt, user_prompt)`）。
3. `src/provider/deepseek.rs`：`DeepSeekProvider`（HTTP）。
4. `src/mcp.rs`：`#[tool]` / `#[tool_router]` で `plan` ツール定義（`PlanParams` + Schemars）+ 検証 + `build_system_prompt()` / `build_user_prompt()` + エラー変換。
5. `src/main.rs`：tracing(stderr) → キー読取 → 起動。
6. `tests/`：上記テスト一式。
7. `cargo fmt --check && cargo check && cargo test`。
8. Antigravity への stdio 登録手順を SPEC/README に追記（外部設定なのでドキュメントのみ）。
9. 実 API スモーク 1 回。
